# 背景

[English](background.md) | 日本語

Acervus が今の作りになっている理由です。各ブロックの働きは [Heap と Horreum](heaps.ja.md) にあります。

## 設計

1種類のアイテムを、チェストでは表せない数だけ保持するブロックです。

中身は2つの値だけです。どのアイテムか、そしていくつあるかです。個数はスロットに分かれておらず、スタックの上限にも縛られません。

**気を配るべきところはすべて境界にあります。** アイテムスタックは64を超える個数を持てます。しかしそれを扱う経路の多くは、行き着いた先で個数を切り詰めてしまいます。バニラの経路も他の Mod の経路も同じです。この種の Mod が壊れるのは決まってそこです。そこで数は内部に持ち、外に出るものは常に普通のスタックにしています。

そのため個数は **long** 型です。外部がこの値を保持することはないので、外部が扱える必要もありません。気を付けるのはゲームが int 型で問い合わせてくる3か所だけで、そこでは返す値を範囲内に収めています。工場が動き始めれば20億はすぐそこです。

**窓口は正直に答えるスロット1つです。** 全体の個数をそのまま報告し、取り出すときは求められた量をそのまま渡します。どちらも重要です。そして片方は `IItemHandler` の Javadoc の記述から意図して外れています。

- `getStackInSlot` —「結果のスタックサイズはアイテムスタックの最大サイズを超えて**もよい**」。これは守っています。スタック1つ分に丸めるのは慎重さではなく嘘です。外部ストレージが InfChest を読むと10万個あるものを64個と報告するのはこのためです。
- `extractItem` — 結果は「`amount` **および** `getMaxStackSize()` 以下でなければならない」。**これは守っていません。** 出ていく量を縛るのは `amount` だけです。

2つ目を破っているのは見落としではなく慣例です。InfChest 自身のハンドラは `totalCount().min(amount)` で、スタック上限での制限はありません。無制限アップグレードを付けたパイプが InfChest を空にできるのはまさにそのためです。この条項を守ると Heap からは1回の呼び出しにつき1スタックしか出せません。1ティックに1回問い合わせるパイプが相手なら1ティックに1スタックです。これを正当なやり方で取り戻す方法はありません。中身を多数のスロットに分ければ取り戻せますが、それでは Heap がチェストのように見えてしまいます。この分野の Mod でそういう作りのものは他にありません。

**どれも何かが強制しているわけではありません。** `IItemHandler` は Javadoc 付きのインターフェースにすぎず、返されたサイズを検査するコードはありません。`ItemStack` は個数を素の int で数えるので、1スタックに20億個あってもそのまま正当です。実際にある制約はもっと狭く、正確に知っておく価値があります。

| | |
|---|---|
| 強制される | `ItemStack.count` は int 型 — 2,147,483,647 が上限 |
| 強制される | バニラのコンテナのスロットは**格納するとき**に `getMaxStackSize()` まで切り詰める。そのため大きすぎるスタックを普通のチェストに入れると超過分が失われる |
| 強制されない | 上の Javadoc の内容すべて |

つまり防護柵はあるのではなく無いのです。保証は規律から作るしかありません。次の節が重要なのはそのためです。

**このブロックは意図して `Container` にしていません。** ブロックがコンテナとアイテムハンドラの両方を備えているとホッパーはコンテナの経路を優先します。そして64個ずつのスロットで数十億個を表そうとするコンテナは、まさに壊れる形をしています。[InfChest](https://github.com/Kotori316/InfChest) はホッパーをその経路から外すためにミックスインを同梱する必要がありました。そもそもコンテナでなければ同じ修正をもっと早い段階で済ませたことになります。

**つるはしは速く壊すための道具で、壊す条件ではありません。** 金属とガラスのブロックなら `requiresCorrectToolForDrops` を付けたくなります。実際このブロックにも付いていました。ところがどの採掘タグにも入っていなかったので、正しい道具が一つも存在せず Heap は何もドロップしませんでした。正しく設定したとしても割に合いません。中身は替えが利かず、つるはしを忘れたことは20億個のアイテムを消す理由になりません。そこでこのブロックは速度のために `mineable/pickaxe` に入れ、ドロップには何も要求しないようにしています。

**中身はドロップしたブロックに乗って運ばれます。** 設定でも選択でもありません。容量いっぱいなら中身は20億個のアイテムで、それを地面にばらまけば3100万個のエンティティになります。それがうまく終わる形はありません。そのため Heap はシュルカーボックスと同じように自分の中身を持ち運びます。先に空にするものではなく、そのまま動かすものです。これが持ち歩ける倉庫になるのを抑える手段はドロップの挙動ではなく容量です。容量のほうは*設定*できます。

そのため Heap はアイテムの状態でもツールチップに中身を表示します。この行がなければ20億個のダイヤモンドを入れた Heap は空の Heap と見分けがつきません。アイテムがそのまま嘘をついていることになります。

**中身はブロックに描かれます。** アイテムはガラスの中に浮かび、見ている人の方を向きます。量はふさがれていない各面に看板のように平らに書かれます。カメラの方を向くラベルにしたところ、面に対して斜めに立ってブロックにめり込み、数字の端が切れてしまいました。

**いくつの面が同時に動いていても、アイテムが増えることも消えることもありません。** この種のストレージブロックが複製を起こす原因は少数に限られます。ここではその一つ一つに対処し、議論で済ませずテストで固定しています。

| 起こり方 | 防いでいるもの |
|---|---|
| シミュレーションの答えが実際の答えと食い違う | どちらも同じ状態から、問い合わせられたその時点で算出する |
| 挿入処理が渡されたスタックを黙って減らし、呼び出し元の手元にも残り Heap にも増える | 渡されたスタックには一切触れず、入りきらなかった分だけを返す |
| 面ごとのハンドラがそれぞれ自分の状態を覚えている | ハンドラは1つだけで、何も覚えていない |
| 壊したときに中身がばらまかれ、ドロップしたブロックも中身を持っている | このブロックはコンテナではないので、ばらまくものがない |

さらにすべての面に**同じハンドラのオブジェクト**を渡しています。1つの Heap にハンドラが2つあれば、古い答えが残りうる場所が2つになるからです。

最後の行は [InfChest がリリースしてしまった](https://github.com/Kotori316/InfChest/commit/52aec050)不具合で、21.8.1 で修正されました。`spillsNothingWhenBroken` が実際のワールドで実際のブロックを壊し、地面に落ちたものを数えるのはこのためです。並行処理への備えは必要ありません。ブロックエンティティはすべてサーバースレッドで操作されるからです。競合状態に見えるものは、実際には上の表のどれかです。

## 使い方

**右クリックします。** 画面は他の3種類の Heap と同じ並びです。中身・バー・容量に対する個数・両側のスロットが並びます。

| | |
|---|---|
| 何かを持って **In** をクリック | それを入れる |
| 何かを持って **In** を右クリック | 1個入れる |
| **Out** をクリック | 1スタック取り出す |
| **Out** を右クリック | 半スタック取り出す |
| **Out** をシフトクリック | インベントリに入るだけ取り出す |
| 自分の持ち物をシフトクリック | すべて入れる |

このどれもこの Mod が書いたものではありません。ゲーム自身のスロットの扱いです。Heap をスロットとして見せている理由もそこにあります。**アイテムなのだから、アイテムと同じように扱えるべきです。** 以前の版ではかわりにボタンがありました（1スタック取る・1個取る）。しかしプレイヤーがすでにできていた操作に対して、ボタンは新しく覚えることを増やすだけでした。

ワールドに置いたまま、何も開かずに操作できます。

- **中身と同じものを持って右クリック** — そのスタックを入れます。
- **中身と同じものを持ってスニークしながら右クリック** — 持っているその種類のものをすべて入れます。

それ以外のものを持っているか何も持っていなければ画面が開きます。問題は Heap がそれを*すでに持っている*かどうかで、*受け入れる*かどうかではありません。空の Heap は何でも受け入れます。中を見ようと右クリックしただけのプレイヤーが、手に持っていたものでブロックの用途を決めてしまうことになります。空の Heap を何に使うかは画面で決めるか、パイプに任せるべきです。パイプが決めることこそパイプの役目です。

「1スタック」は常にそのアイテムの1スタック分を指し、64個ではありません。スタックサイズを変える Mod はよくあるので、固定の数値ではそうした Mod の下で誤りになります。

**数は2通りの書き方で表示します。** 部屋の向こうから見るブロックと、ひと目で見る画面には大きさを示します。最大3桁・小数点以下は最大1桁・単位付きです（`100M`・`2.1G`・`999.9T`）。短縮された数にはカーソルを合わせれば元の数が表示されます。個数・残り容量・スロットのどれでも同じで、`2,000,000,000` のように数そのものを答えます。略した数は常に元の数を示せるべきです。そうでなければ略記は要約ではなく損失です。

単位は国際単位系の接頭辞（K・M・G・T・P・E）です。6つの1文字で long 型の全範囲をまかなえます。`Long.MAX_VALUE` はおよそ `9.2E` です。英語のショートスケールによる略記は小さい側では自然に読めます。しかし T で尽きて、その先は誰も知らない綴りになります。また AE2 が保存アイテム数に付けているのもこの単位なので、使ったことがある人はすでに覚えています。

3桁であることは、短い形で桁区切りを不要にする理由でもあります。区切るべき4桁目がそもそもありません。2つの形はどちらも `Counts` の1か所にまとめています。同じ中身についてブロックと画面の表示が食い違うと、誰も気付かないまま誰もが信用しなくなるからです。

**Heap は中身のあらゆる形を受け入れます。** あるアイテム9個（または4個）が別のアイテム1個にクラフトでき、損失なく元に戻せる場合があります。金属の塊・インゴット・ブロックや、スライムボールとスライムブロックなどです。そうした形のどれかの Heap は他の形も受け入れ、最初に入った形で数えます。手で取り出してもパイプで取り出しても、出てくるのは常にその最初の形です。この対応はゲーム自身のレシピから読み取るので、他の Mod の形も含まれます。

内部では Heap は最小の形で数えるので、端数が切り捨てられることはありません。インゴットの Heap に入れた塊4個は塊4個のまま残ります。画面の **Out の文字をクリック**すると Out スロットが最小の形に切り替わります。それらの塊や、その形の他のものを取り出せます。スロットにはどの形を出しているかが表示されます。

**ゲームが中身を認識できなくなった Heap も中身を保持します。** Heap の中身を追加している Mod を外すと、Heap にはテクスチャ欠落の市松模様と保持していた ID が表示されます。手でもパイプでも何も受け入れず、何も出しません。Mod を戻せば元どおりです。

**空になった Heap は何を入れていたかを忘れます**（Locked の場合を除く）。覚えたままの Heap は次に入れようとしたものを拒否してしまいます。しかもブロックにはその理由を示すものが何もありません。

**Heap の画面右上のボタンで今の中身に固定できます。** 赤が Locked・灰色が Free です。Locked の Heap は空になっても種類を保ち、他のものを受け入れません。自動化したラインが先に間違ったもので埋めてしまうことを防げます。Locked にできるのは中身がある Heap だけです。空の Heap を Free に戻すと種類を忘れます。エネルギーには種類がないので、その画面にはボタンがありません。

### Fluid・Energy・Gas Heap

この3つは Item Heap と同じ画面です。中身・バー・容量に対する量（`12.3K B / 1G B`）が並びます。2つのスロットには容器を入れます。バケツ・タンク・バッテリーなどです。

| スロット | 働き |
|---|---|
| **In**（左） | 容器の中身を Heap に移す |
| **Out**（右） | Heap から容器を満たす |

方向を決めるのはスロットで、容器の満ち具合ではありません。そのため半分入ったタンクはどちらにも使えます。それ以上移せなくなった容器は取り出すまでスロットに残ります。インベントリから容器をシフトクリックすると、空の容器は **Out** に入り、それ以外は **In** に入ります。

**バーをクリック**すると長さの意味が切り替わります。カーソルを合わせるとどれを表示中かがわかります。選択はプレイヤーごとにクライアント設定（`screen.barScale`）に保存されます。

| 目盛り | バーが満杯になる値 |
|---|---|
| **線形**（既定） | 容量 — `600G / 1T` で10分の6 |
| **対数** | 容量。10の累乗ごとに目盛りが1つ — `1K / 1T` で4分の1 |
| **桁内** | 次の10の累乗 — `55K` で `10K` から `100K` までの半分 |

桁内のときはバーにカーソルを合わせると、桁を10の累乗で示します（`10⁴ - 10⁵`）。

ワールドに置くと Fluid Heap と Gas Heap のガラスは中身で満たされて見えます。Energy Heap は設置した人の方を向いた閉じた筐体で、正面に12個のランプがあります。容量までの10の累乗を12等分し、その1つ分ごとに点灯するランプが1つ増えます。既定の1兆なら10倍ごとに1つです。どの Heap もふさがれていない各面に量を看板のように平らに書きます。Energy Heap だけは正面にのみ書きます。

### 持ち運ぶ

Heap は壊しても中身を保つので、インベントリ内の Heap は中身の入った Heap です。これまでは何もそれを読んでいませんでした。今は違います。**持ち歩いている Heap はアイテムを集めます。**

- **中身と同じものの上を歩く**と、それはスロットではなく Heap に入ります。音もアニメーションもそのままです。インベントリが受け取るより先に入るので、インベントリが満杯でも妨げになりません。
- **別の経路でスロットに入ったもの**（`/give`・クラフトの結果・チェストからのシフトクリックなど）も少し後で回収されます。Heap の中身がスロットを占めることはもうありません。
- **スニークしながら空中を右クリック**すると手に持った Heap が開きます。ブロックと同じ画面で、スロットも数字も同じです。

4種類の Heap はすべてこの方法で開けます。Item Heap だけではありません。手に持った Fluid・Energy・Gas Heap はブロックとまったく同じ表示で、**In** には今も容器を入れられます。バケツ・バッテリー・タンクの中身がそこに移ります。持っている間は **Out** には何も入りません。

**手に持っているものには手を付けません。** これが逃げ道です。Heap に回収されてしまうものを手元に残しておける唯一の場所です。着ている防具も同じ理由で対象外です。コンテナを開いている間も何も回収しません。そのときは意図して物を動かしていて、その中の1つが Heap かもしれないからです。

**取り込むだけです。** 再び設置するまで Heap から何かが出てくることはありません。手に持った Heap の画面には*預け入れのみ*と表示され、その言葉どおりです。この非対称は未完成の半分ではなく設計そのものです。

- 取り込めることがスロット1つを割く価値になります。ホットバーに石の Heap を入れておけば、採掘の遠征で埋まらないスロットが1つで済みます。それこそこの Mod が存在する理由です。
- 取り出せたらゲームが終わってしまいます。どんなものでも20億個がポケットから手に入り、ブロックを置く必要も近くに立つ必要もないとなれば、他のあらゆるストレージは無意味になります。何かを持ち歩く理由の大半も消えます。ブロックを置くことは中身を引き出すための代価で、ある場所で行う小さく意図的な行為です。

規則とそれぞれの理由です。

| | |
|---|---|
| 中身として**すでに持っている**アイテムだけを取り込む | 鞄の中の空の Heap が最初に踏んだものに用途を決められてしまうため |
| スロットに**単独で**ある Heap だけが取り込む | 1つのスロットに重なった複数の Heap はコンポーネントを共有するので、その Heap を満たすと全部が満たされるため |
| スタックは各 Heap に**分け合い**、それぞれに丸ごとは渡さない | 何個の Heap に問い合わせても10個は10個のままでなければならないため |
| 投げたばかりのアイテムや他人のために確保されたアイテムには**手を付けない** | バニラが確認する2つの条件と同じものを1段階早く確認している |
| **アイテムにはハンドラがない** | そのためパイプ・バックパック・他の Mod もスロットにある Heap から中身を抜き取る方法を見つけられない |

唯一の例外は画面です。**手に持った空の Heap は画面で意図して用途を決められます。** 画面を開いて何かを入れるのは決断です。花の上を歩くのは決断ではありません。空の Heap の用途を決めてよいのが意図的な経路だけなのはそのためです。

`[item]` の `absorbsWhenCarried = false` で無効にできます。

画面はブロックのものをそのまま使っていて、別に作ったものではありません。`Pile` はアイテムの Heap の本体です。どこに置かれているかを問わない計算部分です。`HeapBlockEntity` と `CarriedHeap` はそれを置ける2つの場所です。スロット・メニュー・画面は以前はブロックを相手に書かれていました。今は `Pile` を相手に書かれているので、同じ3つがどちらの場所でも動きます。両者を分けるのは `gives()` という1つのメソッドだけです。

## Horreum

9 個の Heap を収め、そのすべてに 1 か所から手が届くようにするラックです。発想の元は Industrial Foregoing の [Black Hole Controller](https://ftb.fandom.com/wiki/Black_Hole_Controller) です。近くのストレージを探しに行くものではなく、ストレージを*中に入れる*箱です。

ここではほとんど手間をかけずに収まります。**Heap はもともと中身をアイテムとして持ち歩いている**からです。そのためラックは自分では何も保存しません。Heap アイテムを入れる 9 個のスロットがあるだけで、外に出す窓口はどれもその中身を映したものです。何も複製されず、歩調を合わせ続ける必要もありません。Heap を引き抜けば中身も一緒に出ていきます。中身ははじめからほかのどこにもなかったからです。

12 個まで入った頃のラックでは、9 個目より後の Heap が中で待っています。それぞれ次に空いたスロットへ移ります。ラックを壊したときはラックと一緒に運ばれます。

置いたラックは置いた人の方を向きます。前面には 9 個のスロットそれぞれにランプがあり、画面と同じ 3×3 の並びです。Heap が入っている間はその Heap 自身の色で灯るので、Item Heap・Fluid Heap・Energy Heap・Gas Heap を見分けられます。

**わざと混在させています。** 1 台のラックに Item Heap・Fluid Heap・Energy Heap・Gas Heap を並べて入れられ、それぞれに合った窓口を出します。アイテムハンドラー・液体ハンドラー・エネルギーストレージ、それに Mekanism が入っていれば化学物質ハンドラーで、どれも同じブロックに付きます。4 台のラックに仕分けると、ひとつのことを言うためにブロック 4 個とパイプ 4 系統が要ります。

| | |
|---|---|
| アイテム | **ラックのスロット 1 個につき窓口のスロット 1 個**。常に 9 個なので、Heap を取り出してもパイプが覚えている番号はずれません |
| 液体・ガス | **実際に入っている Heap 1 個につきタンク 1 個**。`fill` と `drain` は番号を受け取らないので、ティックをまたいで番号を持ち続けるものはありません |
| 液体やガスを入れるとき | 空の Heap を使う前に、**すでにそれが入っている** Heap へ入れます |
| エネルギー | **ひとつの共有の蓄え**。`IEnergyStorage` には番号がまったくありません。エネルギーには種類がないからです |
| 壊したとき | 中の Heap ごと運ばれます。Heap が中身を持ち歩くのと同じ理由です |

アイテムはスロットが固定で、液体は固定ではありません。これを決めているのはインターフェースです。`IItemHandler` は*搬入と搬出のときに*スロット番号を受け取ります。そのためパイプはあるティックでスロットを選び、次のティックでそこを操作できます。番号は動かずにいなければなりません。`IFluidHandler` は番号を受け取りません。`fill` と `drain` に渡されるのは対象の液体と量です。番号はタンクを読むときにしか使われず、それも問い合わせがあったティックの中だけです。タンクを 12 個に固定するのは慎重な答えでした。しかしブロックのタンクを一覧にするものでは「空」と表示されるバーが 11 本いつまでも並びました。

**しゃがんで空中を右クリックすると**持ち歩いているラックを開けます。Heap と同じです。中の Heap は動かせますが、*Heap の中身*には手が届きません。持ち歩いているものはどれも中身への窓口を出さないからです。持ち物から Heap を取り出すのはアイテムを動かすことで、蓄えから引き出すことではありません。

**中の Heap は中身を出します。** ポケットの中の Heap とは違います。これはアイテムの問題ではありませんでした。Heap から引き出す代価はブロックを 1 個置くことで、ラックがそのブロックです。違いは値 1 つだけで、Heap を見つけたファクトリがどちらかに設定します。

### ツールチップの中身

どの Heap も中身を絵で描きます。アイテムならそのアイテム自体を描き、液体や化学物質ならそれ自身の画像を描きます。どちらも名前と量の横に並びます。ラックは Heap 1 個につき 1 行を描くので、何も開かずに 9 個の Heap を読めます。

行の羅列ではなく絵にしているのは、ラックには 9 個あるからです。文章が 9 行あるツールチップは誰も最後まで読みません。エネルギーにはアイテムも専用の画像もないので、稲妻を描いています。ほかの行に絵がある場所に穴が空いた行は、空ではなく壊れているように見えるからです。

**ラックの Heap をどう書き留めるかを知っているのは 1 か所だけ**で、`HorreumBlockEntity` です。これは痛い目を見て得たものです。以前は 4 か所がそれぞれ自前で形を書き出していて、持ち歩き中のラックだけ書き方が違いました。アイテムの一覧を `Heaps` の下に入れ子にせず、コンポーネント全体として書いていたのです。そこが 1 回書くと残りの 3 か所は何も見つけられません。そのため持ち物の中のラックから Heap を 1 個取り出すと残りの 11 個が消えたように見えました。実際には残っていましたが、読めるところがありませんでした。個数の名前が 1 種類の Heap では `Count`・3 種類では `Amount` だったときと同じ間違いです。2 か所以上で知られている形は、いずれ自分自身と食い違います。

読み取りはクライアント側の `HeapContentsTooltip` で行い、ツールチップを求められる場所では行いません。`Item#getTooltipImage` に渡されるのはスタックだけで、ほかには何もありません。Heap を読むにはレジストリが必要です。クライアントはそれを持っていますが、アイテムは持っていません。そのためコンポーネントはスタックを運び、運ぶのはスタックだけです。

## 任意の Mod

Acervus に必要なのは **NeoForge だけ**です。Mekanism と Refined Storage は入っていれば気付くものであって、必須ではありません。どちらもコードを読んで期待するのではなく、mods フォルダーを空にしてテストを走らせて確かめています。

**Mekanism** があると Gas Heap は化学物質を入れられ、パイプとやり取りできます。ただし Gas Heap 自体は Mekanism の有無にかかわらず存在します。ワールドから Mekanism を外しても Gas Heap はその場に残ります。入っていたものはゲームが読めない中身として保たれ、Mekanism が戻るまで市松模様の表示のまま何も出し入れできません。作れるのは Mekanism が入っているときだけです。

**Refined Storage** に対しては 1 つだけ用意しています。Heap を `long` で読む外部ストレージプロバイダーです。RS はどこでも `long` で数えます。`ResourceAmount` は `long` を持ち、`insert` と `extract` も `long` を受け取ります。Heap も `long` を持つので両者は完全に一致します。これまで両者は `IItemHandler` を介して話すしかありませんでした。その `ItemStack` は `int` で数えます。そのため 50 億入った Heap を見たネットワークには 2,147,483,647 と伝わり、ネットワークはそれを信じていました。制限は RS 側にはなく、間をつなぐアダプターにありました。外部ストレージを Heap か Horreum に向ければ、ネットワークには本当の合計が伝わります。

RS はブロックに当てはまる外部ストレージプロバイダーをすべて使い、それぞれの報告を足し合わせます。そして RS 自身のアイテム用と液体用のハンドラープロバイダーは Heap に必ず当てはまります。そのため Heap のプロバイダーは `int` を超えた分だけを報告します。それらのハンドラーが運べない部分です。合わせるとアイテムでも液体でも Heap の本当の個数になります。今後の RS がこの足し合わせ方をやめたら、グリッドに表れます。RS を更新したら Heap の個数とグリッドの個数を見比べてください。

RS は API の成果物を公開していません。Central にも ModMaven にもありません。そのため依存先は Modrinth の Maven にある RS 本体の jar で、バージョンを固定しています。ファクトリは `null` を返さず、必ずプロバイダーを返します。RS は `.map(factory -> factory.create(…)).toList()` でそれらを集め、返ってきたものを選別しないからです。ほかの Mod のブロックに対して「ここには何もない」と答えるプロバイダーこそ、インターフェースが実際に求めている形です。

口で言うのは簡単ですが、テストするまでは本当ではありませんでした。`GasHeap.present()` はまさに正しい確認処理に見えましたが、動くはずがありませんでした。静的メソッドを呼ぶとそのメソッドがあるクラスが初期化されます。そして `GasHeap` は静的フィールドに `BlockCapability<IChemicalHandler, …>` を持っています。つまり「Mekanism はあるか」と尋ねると、それを確かめるために Mekanism のクラスを読み込んでいました。Mekanism がなければ Mod は構築中に落ちていました。**確認処理を、それが守っている扉の向こう側に置くことはできません。** 今は `Mods` に置いてあり、そこではほかの Mod に属するものを一切名指ししていません。

2 つ目はもっと目立たないものでした。`mineable/pickaxe` タグは Gas Heap を必須の項目として載せていました。必須項目が存在しないブロックを名指ししていると、その項目だけが抜け落ちるのではありません。タグファイル全体が拒否され、4 つのブロックすべてがそろってタグから外れます。Mekanism がなければツルハシで掘っても Heap は素手と同じ速さでした。今はこの項目を任意にしてあり、条件なしで書き出しています。これで生成されるファイルが `run/mods` にたまたま何が置いてあるかに左右される落とし穴もなくなりました。

どちらも mods フォルダーから Mod を取り除いてテストを走らせて見つけました。新しい Mod に頼るたびに、もう一度やる価値があります。

## 決めたこと

- 左クリックでは取り出しません。左クリックは Heap を壊す操作のままにしています。
- ブロック上の個数は画面と同じ規則で短縮します。
- Heap は強化できません。どの Heap も設定された容量を持ちます。それがこの仕組みの要点です。
- 中身のある Heap はその種類に固定できます（*使い方* を参照）。
- レシピ。Heap は種類を決める部品（チェスト・大釜・レッドストーンブロック・オスミウムブロック）を、鉄ブロック 4 個・ネザースター 2 個・ネザライトインゴット 2 個の枠で囲んだものです。ラックは空の Heap をネザースター 4 個とネザライトインゴット 4 個で囲んだものです。材料はどれもスタックできます。Heap は数をそろえて作るものだからです。鉄とネザースターは装置で集められますが、ネザライトだけは掘るしかありません。
